# 0006 — Downloading, converting and pack building move from the plugin into the disc bot

**Context:** Upstream URLCustomDiscs (and our fork after ADR 0003) downloads yt-dlp, Deno and FFmpeg into the Minecraft container at runtime and runs them there, inside the process tree that has the whole world on disk, competing with the game for CPU. We had started pinning and checksumming those downloads. **Decision:** the disc bot's image ships the tools at build time (FFmpeg from Debian, yt-dlp + yt-dlp-ejs from PyPI, Deno copied from the official `denoland/deno` image) and does all of it: download, convert to Ogg Vorbis (trimmed to `MAX_SECONDS`), store `tracks/<name>.ogg`, write `discs.json`, rebuild the disc pack and its `.sha1`. One job at a time, CPU-capped in compose. The plugin keeps only what must run in the game: `/disc` commands, the jukebox, giving discs, pushing the pack. `/disc create` and `/disc delete` call the bot's `POST /api/create|delete` with a shared secret (`DISC_API_SECRET`; like `PACK_TOKEN`, generated once by the bot and saved to `.disc-secrets.json` in the shared folder, where the plugin reads it, so nothing is copied by hand) and relay its streamed progress to the player. The Minecraft server only holds data files (MP3 drop folder, tracks, `discs.json`, pack). Supersedes the "runs on this server" part of ADR 0003 and the plugin-side hashing in ADR 0005. **Why:** no runtime binary downloads in the Minecraft container, so the checksum/pinning problem disappears; heavy work can't stall ticks; ~1,500 lines of Java installer/zip code are deleted. yt-dlp stays current via `pip install -U` into the bot's own user site (at startup and from `/disc updatedep`). Cost: the bot must be up to create discs (existing discs keep playing), and the API is reachable through the bot's public domain, guarded only by the secret. Upgrade path: put the bot on the Minecraft service's Docker network and stop routing `/api` publicly.
